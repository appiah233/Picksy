# Sanity vertical integration proposal

**Status:** PROPOSED for Gemini/Codex cross-review; no Studio, dataset mutation, or public catalogue switch has been verified. **Project:** `0tozsrrx`; **dataset:** `production` (product-owner supplied).

## Ownership and boundaries

The Studio is a standalone sibling of `Picksy`, at `../studio-picksy`. Gemini owns Studio schemas, importer tool UX and frontend integration. Codex owns the importer backend, caller authorization, Sanity draft write boundary, and validated public catalogue adapter. The existing `/admin`, Auth.js and Prisma paths remain in place pending disposition.

1. Studio tool submits source ID and URL to the Picksy importer service. The service validates caller identity and editor permission **before** URL/DNS work. Source allowlist, permission reference, SSRF protection, connection/redirect checks and normalization remain server-side. No source is live until actual retrieval permission and credentials are documented.
2. The resulting `ProductImportCandidate` remains a preview with field provenance. Saving creates or updates a **Sanity draft** only. Source identity (`sourceId`, canonical URL, external product ID when present) must support duplicate detection, and an expected revision must prevent lost edits. Ordinary Sanity document IDs should be generated by Sanity; do not derive them from product slug. Preserve the Sanity `_id` returned by creation for later edits. [Sanity Actions](https://www.sanity.io/docs/content-lake/dispatch-actions) support draft/version operations and transactions.
3. Human editors complete category, product, merchant destination, review, offer and disclosure data in Studio. Publication is a separate human action. The Picksy public catalogue adapter reads **published** documents only, maps them into `CatalogRecords`, runs `validateCatalog`, and exposes only records passing the full Gate 3 checks. It must fail closed on broken references, duplicate identities, missing editorial review or merchant authorization; no document can self-assert that its destination is approved merely by containing a URL.
4. Keep `src/content/catalog.ts` as the public source of truth until an integration test demonstrates draft isolation, approved publication, invalid-record rejection, Next.js rendering and public regression behavior. The cutover and cache/revalidation strategy require a reviewed contract amendment.

## Authentication proposal requiring review

Sanity Studio controls its own editor sign-in and dataset roles. A separate Picksy API does **not** inherit that authentication. A shared robot token in Studio browser code would authorize anyone who extracts it and cannot distinguish or revoke individual editors; reject that pattern. [Sanity's Studio authentication guidance](https://www.sanity.io/docs/app-sdk/sdk-authentication) describes user session tokens in Studio, while [token guidance](https://www.sanity.io/docs/content-lake/http-auth) distinguishes personal/user and robot tokens.

Proposed proof: determine whether the Studio can safely pass a current editor credential to the Picksy service over HTTPS; the service must validate it online against Sanity and check effective permissions for project `0tozsrrx`, the dataset and intended operation on **every request**. Do not assume the credential is short-lived or exportable: [Sanity documents differing Studio token/cookie modes](https://www.sanity.io/docs/app-sdk/sdk-authentication), and [personal tokens can last a year](https://www.sanity.io/docs/content-lake/http-auth). The [Access API permission-check endpoint](https://www.sanity.io/docs/http-reference/access-api) is a candidate for the live proof, provided it establishes a human actor rather than a robot. Confirm the exact supported verification and transport before implementing or freezing the contract. Use a separate, server-only Sanity robot write token solely for service-to-Content-Lake draft mutations, never as proof of editor identity. Reject anonymous, expired, wrong-project and insufficient-role calls before network/source work; avoid logging any bearer credential. If Sanity cannot provide a safe supported handoff to a standalone API, evaluate a trusted Sanity-hosted Function or a narrowly scoped application auth boundary before enabling the importer.

SecurityAgent review on 2026-10-10 classified a browser-shipped shared `x-picksy-importer-token` or robot token as a **critical blocker**. [Sanity explicitly warns against tokens in browser JavaScript](https://www.sanity.io/docs/help/js-client-browser-token). Restrict CORS to exact Studio origins, but do not treat CORS as authentication; cookie mode additionally needs Origin/CSRF checks. For catalogue invalidation webhooks, verify the raw-body signature, bound replay window and idempotency, then re-fetch current published state; [Sanity webhooks can be duplicated or delivered out of order](https://www.sanity.io/docs/content-lake/webhook-best-practices). The public adapter must explicitly request the [published perspective](https://www.sanity.io/docs/content-lake/perspectives) before `validateCatalog`.

## Schema mapping for Gemini review

| Studio document | Required Picksy fields | Publication concern |
| --- | --- | --- |
| `category` | stable external ID, slug, name, description, audience | published category required for published product |
| `product` | slug, category reference, name, official source, summary, intended user/workflow, import provenance | no draft in public results; unique slug |
| `review` | product reference, author, dates, methodology, sources, strengths, limitations, suitability, conclusion | complete review before public product |
| `merchant` | name, exact approved hostnames, approved destinations with authorization references | destination approval is editorial evidence, not inferred from the imported URL |
| `affiliateOffer` | product and merchant references, approved destination reference, label, disclosure, active state | at most one active offer per product; safe outbound link |
| `importDraft` | source IDs/URL, candidate, provenance, edits, revision, timestamps | private editing; no automatic product publication |

These are proposed logical shapes, not final Sanity schema names. Gemini should choose Studio schema fields and map them explicitly to the frozen `CatalogRecords` and `ProductImportCandidate` types. Avoid duplicating a mutable publication state when Sanity draft/published identity already expresses it; the adapter can derive Picksy's `state` for validation. Exact schema and query projections require joint review before either side implements them.
